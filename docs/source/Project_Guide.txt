1. About this guide
This guide supports Semester_Project_Description.pdf. The description says what to build. This guide gives
the data formats, interfaces, setup steps, templates and tips to build it. Field lists and numbers here are
minimums: you may add to them. Module names (M1 to M14) are the same as in the description.

4. Repository, git and local setup

4.1 Repository layout
  README.md                      how to run everything, step by step
  docs/                          report, decision records, AI-usage log
  services/                      gateway, ui, orchestrator, scouts, tools, kb, analyst,
                                 ideation, validators, scorer, verdict, critic, agentops
  jobs/                          ingestion, finetune, evaluation
  rubrics/ config/ eval/         rubrics (versioned), weights and thresholds, labelled sets
  k8s/                           manifests (or Helm / Kustomize)
  .github/workflows/             pull request checks         Jenkinsfile   delivery pipeline
  docker-compose.yml             local development

You may group services differently, but each module is its own deployable unit with its own Dockerfile.

4.2 Git workflow
      Create the repository on day 1. Protect main : no direct pushes, pull requests only, required status
      checks, one review from the other member.
      One issue per task, linked to its pull request. Small branches with one purpose.
      Conventional commits: feat(verdict): add duplicate gate , fix(kb): dedupe by url , test(scouts): add
      source failure case .
      Create one merge conflict on purpose (two branches edit the same lines), resolve it in a pull request,
      and keep the screenshot.

4.3 Local setup
  1. Install Docker, kubectl and a local Kubernetes (kind, minikube or k3d). Choose one whose network
     plugin enforces NetworkPolicy (Section 9.3).
  2. Develop with docker-compose.yml (Postgres, Redis, vector store, your services). Compose is for
     development only. The deployment target is Kubernetes.
  3. Keep settings in environment variables or ConfigMaps. Commit a .env.example with names and no
     secrets.
  4. Write the README so a new person can start the system with a short list of commands.

4.4 Dockerfile pattern
  FROM python:3.12-slim AS build
  WORKDIR /app
  COPY requirements.txt .
  RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

  FROM python:3.12-slim
  RUN useradd -m app
  WORKDIR /app
  COPY --from=build /install /usr/local
  COPY src/ ./src/
  USER app
  EXPOSE 8000
  CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]

One image per module (at least 6 distinct images), multi-stage, non-root, pinned versions, a .dockerignore ,
tagged by commit SHA (never only latest ), and scanned in CI.

5. Data collection and ethics
      Official APIs first. Hacker News (Firebase API), GitHub (REST API), Reddit and Product Hunt (official
      APIs with keys). Avoid scraping HTML where an API exists. For any site read its terms and robots.txt .
      Respect limits. Per-domain rate limits, a clear User-Agent, caching, back-off on errors.
      No logins, no private data. Keep only what an idea card needs (name, public text, public URL).
      Credit sources. Every card keeps its source and URL, and the verdict card links to them.
      Fetched text is data. It may contain instructions aimed at models. Never obey it (M12).
      Keep a snapshot of your card data so your system does not depend on a website being up.


6. Fine-tuning
The goal is not a smarter model than a hosted one. It is a cheaper, faster and more consistent model that
follows your rubric format and evidence rule.

6.1 Build the dataset
  1. Collect at least 300 (idea, evidence, dimension) examples from your knowledge base, covering all six
     dimensions and all score levels.
  2. Draft labels with a hosted model using your rubric, then check at least 60 by hand and fix them.
     Mark which ones were checked. Use those for evaluation.
  3. Split by idea, not by row, so one idea never appears in both train and test (for example 80 / 20). Never
     use ideas from your labelled set (Section 10) for training.
  4. One JSON object per line:

  {"messages": [
   {"role": "system", "content": "Score the idea on demand_pain using rubric demand_pain@v3. Reply with JSON
  only."},
   {"role": "user", "content": "IDEA: ... EVIDENCE: [card_8f21#c2] ... [card_77a1#c0] ..."},
   {"role": "assistant", "content": "{\"score\": 3.5, \"confidence\": 0.7, \"evidence_ids\": [\"card_8f21#c2\"],
  \"reason\": \"...\"}"}]}


6.2 Train and serve
      Train on a free GPU (Colab or Kaggle) with LoRA or QLoRA on a 1B to 3B open model, using Hugging
      Face PEFT and TRL or Unsloth. Start with a few epochs, watch validation loss, and record the settings
      (rank, learning rate, epochs, batch size) in the repository.
      Merge the adapter into the base model. Optionally quantise it (for example GGUF) so it runs on CPU.
      Serve it in its own container (llama.cpp, Ollama or a small FastAPI app) behind POST /score , /health ,
      /ready . Do not commit large weights to Git: use a release asset or a registry. Set Kubernetes requests
      and limits from measurements.
      Validate every output against the schema. If invalid, retry once, then fall back to the hosted model and
      log the fallback.

6.3 Evaluate
Run the base model, your fine-tuned model and a hosted model on the hand-checked test examples. Report
in one table: agreement with human scores (mean absolute error and share within 1 point), valid-JSON rate
and share of real evidence ids, latency and cost per score. Add one example where fine-tuning did not help
and explain why.


7. AgenticOps
Run agents the way operations teams run services: see what they did, limit what they spend, test their
behaviour and notice when they get worse (M13).

 Capability                      What to build
 Tracing                         Every agent step, tool call and model call writes a trace record under one run id
                                 (Section 2.3). A replay command re-runs a stored run using recorded tool results.
 Budgets                         Caps on tokens, pages, steps and cost per run, enforced in the orchestrator and tool
                                 layer. Over budget means stop or ask the user.

8.1 GitHub Actions (every pull request)
Lint and type checks, unit tests (including the Verdict Engine), component tests for the UI, a retrieval
quality gate (fails if the score drops below the baseline), Docker build and image scan, and Kubernetes
manifest validation. Make all of them required checks on main .

  name: pr-checks
  on: pull_request
  jobs:
    test:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-python@v5
          with: { python-version: "3.12" }
        - run: pip install -r requirements-dev.txt
        - run: ruff check . && mypy services
        - run: pytest services/verdict -q
        - run: pytest eval/retrieval -q   # retrieval gate
    docker:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - run: docker build -t gateway:${{ github.sha }} services/gateway
        - uses: aquasecurity/trivy-action@0.24.0
          with: { image-ref: "gateway:${{ github.sha }}", exit-code: "1", severity: "CRITICAL" }


8.2 Jenkins (after merge, and nightly)
      A Jenkinsfile with stages: checkout, build and tag by commit SHA, push, deploy to the test cluster,
      smoke test, and (nightly) full evaluation compared with the stored baseline. A failure stops the pipeline
      and nothing is deployed.
      Run Jenkins in a container with access to Docker and your cluster's kubeconfig (a Jenkins credential,
      never in the repository).

  pipeline {

      stage('Build') { steps { sh 'docker build -t gateway:$TAG services/gateway' } }

      stage('Smoke') { steps { sh './scripts/smoke_test.sh' } }

    }
    post { failure { echo 'Pipeline failed, nothing promoted' } }
  }

9.3 NetworkPolicy
      Create a default-deny egress policy for the namespace, then allow DNS, traffic between your services,
      and internet egress only for the M5 pods (selected by label).
      Check that your cluster's network plugin enforces NetworkPolicy. Some default local setups do not. If
      yours does not, use one that does (for example Calico or Cilium).
      Test it: from a non-M5 pod try to reach an external address and show it failing, then do the same from
      M5 and show it working.


10. Tuning the verdict
  1. Build your own labelled set: ideas with profiles and a human verdict for each, including clear GOs, clear
     NO-GOs, borderline cases and thin-evidence cases. Label carefully (ideally both members label
     independently, then resolve differences) and note who labelled what. Use it only for tuning and
     measuring, never for training the scoring model.
  2. Run the system on every labelled idea and build a confusion matrix of your verdicts against the human
     ones.
  3. Change T_go, T_no, floors and weights to improve agreement. Calling GO on an idea experts marked
     NO-GO is worse than missing a good idea, so report that error separately.
  4. Keep the final values in the ConfigMap, and show the before and after matrices in your report. Do not
     fit the values so tightly to your labelled set that they fail on new ideas.
Rubric file. Write one versioned file per dimension, with an anchor for every score from 0 to 5 and at least
one worked example per level:

  dimension: demand_pain
  version: 3
  scale: 0-5      # higher is better for the student
  anchors:
    5: "Five or more independent sources on 2+ platforms show the same recurring
        problem, with growth in the last 6 months."
    3: "Two or three sources show the problem, no clear growth."
    1: "A single weak or old mention."
    0: "No evidence of the problem."
  features: [n_sources, n_platforms, complaint_count, trend_growth]
  output_schema: score, confidence, evidence_ids, reason
  examples:
    - { input: "...", expected: { score: 5, evidence_ids: ["..."] } }

12. Common mistakes
      One long prompt that "does everything", with no limit on retries, debate rounds or spending.
      Caching a verdict without the profile and rubric version in the key, so old answers survive a rule
      change.
      Letting a model, instead of M11, decide or adjust the verdict.
      Scores or claims with no evidence id, or a competitor that is not in the knowledge base.
      Calling the model or scouts directly from the browser, or hard-coding localhost in an image.
      Testing retrieval only by eye, or splitting text without keeping the card id.
      Ideas that are renamed copies of existing products, or that ignore the student's hours.
      Leaving Docker, Jenkins and Kubernetes to the last days. Get a thin version of everything running end
      to end on Kubernetes early, then improve each part.
